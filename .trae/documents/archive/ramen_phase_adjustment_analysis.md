## 原计划 Phase 依赖关系分析

原开发计划定义了 9 个 Phase：

```
Phase 1: 建立核心领域边界 (接口定义)
Phase 2: 配置系统整理
Phase 3: 结构化输出、日志和统计
Phase 4: 基础规则、数值、Flag 和事件
Phase 5: 动作预览与手写策略工具
Phase 6: 实现拉面杯最小闭环
Phase 7: 整理 crate 边界
Phase 8: 批量模拟和性能优化
Phase 9: 删除温泉杯代码
```

关键依赖链：

```
Phase 1 (接口)
  ├── Phase 4 (规则) ──→ Phase 5 (预览) ──→ Phase 6 (闭环)
  ├── Phase 2 (配置) ──→ 可独立
  └── Phase 3 (输出) ──→ Phase 6 (闭环)
```

Phase 4 → Phase 5 → Phase 6 是**强串行依赖**，分开做会导致反复修改接口定义。

## 调整建议

### 核心调整思路

**"先具体后抽象"**：由于拉面杯机制已经明确，不需要先设计通用接口再回头实现。直接在 `ramen` 模块中实现具体类型，从具体实现中自然提取通用部分。

### 建议的新 Phase 划分

#### Phase 1：实现拉面杯核心模块（原 Phase 1 + 4 + 5 + 6 合并）

这是最核心的调整：将原本分散在 4 个 Phase 中的拉面杯逻辑实现合并为一个连续的阶段，分为 4 个子步骤：

**1a - 建立 ramen 模块骨架**

- 在 `crates/umasim/src/game/ramen/` 下新建模块
- 定义 `RamenGame` 结构体（包含 `BaseGame` + 拉面杯特有状态）
- 定义 `RamenAction` 枚举（基础操作 + 吃面组合）
- 定义 `RamenStage` 枚举（普通、地区选择、超级拉面选择）
- 定义拉面杯专用状态字段（诀窍、诀窍槽、隐藏风味、剧本PT、地区选择等）
- 注册到 `game/mod.rs`

**1b - 实现核心游戏机制**

- 诀窍系统：三种诀窍库存管理、队列淘汰（上限10）
- 诀窍槽系统：基础值分配算法、训练额外加成、友情训练加成
- 隐藏风味：获取时机（固定回合 + 友人出行）、使用规则（做面时替代0-2个）
- 做面/吃面：消耗诀窍制作拉面、回合内生效、基础效果+地区效果叠加
- 地区选择：每年选3个地区、范围限制（第1年id0-4，第2年id5-9，第3年id10-19）
- 剧本PT：获取规则（基础值+叠加增量）、RMJ结算（3年阈值）
- 超级拉面：选择阶段、72-77回合自动生效、分身规则
- 分身系统：地区拉面分身（随机不计算得意率）和超级拉面分身（计算得意率）
- 友人系统：登场、点击、解锁、出行（5次）
- 合宿规则：训练等级5、特殊事件
- NPC系统：5个NPC在训练中出现

**1c - 实现动作预览和手写策略**

- `list_actions`：生成所有合法组合动作（吃面/不吃面 + 基础操作）
- `preview_action`：预览动作效果
- 手写策略：基于收益排序和剪枝
- 固定顺序地区选择策略
- 超级拉面选择策略

**1d - 跑通最小闭环**

- 完整回合流程 0-77
- 地区选择（3次）
- 做面/吃面
- RMJ结算（3次）
- 超级拉面（72-77）
- 终局结果输出
- 配套单元测试

**为什么合并 Phase 1/4/5/6？**

1. 拉面杯机制已明确，先抽象再实现是额外开销
2. 规则、预览、闭环紧密耦合。预览必须与真实执行使用相同计算路径，分开做会引入不一致
3. 最小闭环是验证规则正确性的唯一方式，越早跑通越早发现问题
4. 从具体实现中提取通用接口，比从空接口推导具体实现更可靠

#### Phase 2：配置系统整理（原 Phase 2）

内容不变，但执行时机延后到核心闭环稳定后。此时可以准确知道哪些配置项是真正需要的。

#### Phase 3：结构化输出和统计（原 Phase 3）

内容不变，但延迟到核心闭环稳定后。最小闭环可以先使用简单输出。

#### Phase 4：整理 crate 边界（原 Phase 7）

在核心逻辑稳定后，再检查依赖方向，决定是否提取公共 crate。

#### Phase 5：批量模拟和性能优化（原 Phase 8）

在核心逻辑正确、接口稳定后进行性能优化。

#### Phase 6：删除温泉杯代码（原 Phase 9）

所有新代码不再依赖温泉杯后，统一清理。

## 具体调整点

### 1. 开发计划文档中的细节修正

以下内容基于完成后的资料，建议更新开发计划：

- **自动拉面回合**：原计划写"73-78回合"，实际应为**72-77回合**（[ramen_story_flow.md](file:///f:/UmaAI/umaai-rs/.trae/documents/ramen_story_flow.md) 第15条）
- **"食材"术语**：原计划使用"食材"和"万能食材"类比，实际机制为**诀窍(feeling)**和**隐藏风味(special_feeling)**，建议在后续代码中使用准确术语
- **配方概念**：原计划"5个食材=1面"，实际是消耗特定比例的**诀窍点**（每个地区配方不同），且**隐藏风味**可替代0-2个
- **组合动作模型**：原计划概念基本正确，但需注意——非训练操作（休息、外出、比赛）也可以吃面，规则层必须生成所有组合

### 2. 需要新增的独立决策类型

基于确认的回合流程，需要新增以下决策类型（原计划已有提及，但需要明确优先级）：

| 决策类型 | 触发时机 | 优先级 |
|----------|----------|--------|
| 地区选择（3选3） | 回合1/23/47结束时 | **高**（最小闭环前置） |
| 超级拉面选择（3选1） | 回合71结束时 | **高**（最小闭环前置） |
| 吃面/不吃面 + 基础操作 | 每回合 | **高**（核心机制） |
| 友人出行选择 | 解锁后 | **中**（可后续补充） |

### 3. 模块文件结构建议

基于当前代码库结构和拉面杯机制，建议 `game/ramen/` 目录结构如下：

```
crates/umasim/src/game/ramen/
    mod.rs      -- 模块入口、RamenStage 枚举
    state.rs    -- RamenGame 结构体（含 BaseGame + 拉面杯状态）
    action.rs   -- RamenAction 枚举（含组合动作逻辑）
    rules.rs    -- 核心规则（诀窍系统、做面/吃面、RMJ结算、分身等）
    effects.rs  -- 效果计算（基础效果、地区效果、超级拉面效果叠加）
    events.rs   -- 剧本事件处理（含友人事件）
    policy.rs   -- 手写策略（含地区选择、超级拉面选择）
```

### 4. 测试策略调整

原计划 Phase 6 完成后才一次性添加大量测试。建议改为**增量测试**：

- 1b 完成后：测试诀窍系统、诀窍槽算法、做面消耗、配方匹配
- 1c 完成后：测试动作生成、预览一致性
- 1d 完成后：测试完整回合流程、地区选择、RMJ结算、终局结果

## 风险提示

1. **人口密度**：拉面杯共有12个人物（5支援卡+5NPC+1友人+1理事长），比温泉杯更多人，Person 系统的初始化和随机分布需要验证
2. **诀窍槽算法**：基础值分配涉及浮点舍入调整，需要精确的算例验证
3. **分身系统**：两种分身规则差异大（得意率计算、是否包含友人卡），实现时容易混淆
4. **合宿 + 比赛冲突**：夏合宿期间可能有生涯比赛，需要确认优先级
