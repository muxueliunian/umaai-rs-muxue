# 拉面杯模拟器重构开发规划

## 1. Summary

本规划用于在 `main` 分支上重新建设拉面杯回合制游戏模拟器。旧温泉杯实现已保存在 `onsen_backup` 分支，不再作为新架构的兼容目标；新代码应以拉面杯机制为主要需求来源，避免继续围绕温泉杯状态和流程扩展。

总体策略是“新核心、旧实现保留参考”：

- `onsen_backup`：旧温泉杯代码的归档、规则参考和必要时的新旧行为对照。
- `main`：新核心接口、拉面杯剧本、搜索/策略、结构化输出和后续性能优化。
- 拉面杯的固定规则可以直接固化在剧本模块中，不建立过度配置化的通用规则脚本系统。
- 通用部分只抽象真正需要复用的模拟流程、动作决策、统计、日志/输出、配置加载和搜索基础设施。

目标不是把现有仓库机械重写一遍，而是建立一个能支撑拉面杯实际规则、复杂组合决策、高频批量模拟和后续分析的最小清晰架构。

## 2. Current State Analysis

### 2.1 当前仓库结构

workspace 当前包含三个 crate：

- `crates/umasim`：模拟器、游戏状态、搜索、训练员、神经网络和训练数据。
- `crates/umaai`：读取外部游戏状态、文件监控和 AI 推荐入口。
- `crates/analyzer`：分析和模拟工具。

关键入口和模块：

- `crates/umasim/src/lib.rs`
- `crates/umasim/src/game/traits.rs`
- `crates/umasim/src/game/base/`
- `crates/umasim/src/game/onsen/`
- `crates/umasim/src/search/`
- `crates/umasim/src/trainer/`
- `crates/umasim/src/gamedata/config.rs`
- `crates/umasim/src/utils.rs`
- `crates/umaai/src/protocol/`
- `crates/umaai/src/main.rs`

现有规划文档为：

- `.trae/documents/cpu_search_optimization_plan.md`
- `.trae/documents/gpu_acceleration_plan.md`

这些文档中的性能和 GPU 方案作为后续参考，不能将其中旧温泉杯路径视为新系统的既定实现路径。

### 2.2 现有核心抽象和问题

当前 `Game`、`ActionEnum`、`Trainer` 已经形成基本分层：

```text
Game      维护状态、阶段推进、事件和动作流程
Action    修改 Game 状态
Trainer   根据 Game 和候选动作选择索引
```

但接口仍然受旧剧本影响：

- `Game::list_actions` 只返回当前动作列表，无法表达年度选面、组合动作和多阶段决策的上下文。
- `Trainer` 主要返回动作索引，无法自然表达决策请求、候选动作预览、事件上下文和选择原因。
- 事件选择存在 `select_choice` 与 `select_event_choice` 两套接口。
- `OnsenGame` 通过 `Deref` 暴露 `BaseGame`，剧本逻辑直接依赖基础字段布局。
- `OnsenAction` 同时承载普通动作和温泉选择、装备升级、事件选择等特殊流程。
- `FlatSearch`、`MctsTrainer`、`SearchOutput` 直接绑定 `OnsenGame`、`OnsenAction` 和旧训练样本格式。
- `MctsTrainer` 同时承担搜索、特殊策略切换、日志控制、结果保存和分数跟踪。

### 2.3 日志、配置和统计现状

当前配置由 `gamedata/default_config.toml` 和根目录 `game_config.toml` 合并得到，类型集中在 `gamedata/config.rs`。`GameConfig` 同时包含剧本、用户运行参数、MCTS、collector 和旧温泉相关字段，覆盖配置通过 `OverrideGameConfig::merge` 处理，维护成本较高。

当前日志通过 `flexi_logger` 输出到文件和 stderr，并使用全局 logger 以及 `disable_log`/`enable_log` 控制搜索阶段输出。游戏状态、用户可读结果、搜索诊断和程序执行日志仍混在日志或 `println!` 中。多线程 rollout 直接经过可能产生日志的代码，会造成输出交错、锁竞争和无用开销。

当前搜索结果已有均值、标准差、直方图、加权均值等统计，但它们主要服务即时选动作和旧训练样本导出，尚未形成面向回合分析的结构化记录。

### 2.4 现有性能热点

旧 CPU 规划已识别：

- rollout 中频繁 `game.clone()`。
- 每次 rollout 运行大量回合和规则分支。
- rollout 使用较重的手写评估逻辑。
- Rayon 并行搜索中的 RNG 初始化和并行粒度仍可优化。
- rollout 日志调用会产生格式化和同步成本。
- 搜索结果、训练样本和特征提取存在耦合。

拉面杯的动作数量会进一步增加：每个可吃面回合要比较“不吃面 + 基础行动”和“吃面 X + 基础行动”，所以不能把性能优化理解为开发完成后的附加工作；必须在架构层预留静默模拟、状态复制、动作预览和共享回合上下文。

## 3. Domain Requirements: 拉面杯

### 3.1 核心资源

拉面杯围绕诀窍（feeling）和拉面展开：

- 诀窍有 3 种类型（A/B/C），总上限 10，维护获得顺序队列。
- 每回合通过诀窍槽系统获得诀窍，具体分配算法见机制文档。
- 每种地区拉面有固定配方，制作 1 个拉面需要消耗 5 个诀窍点。
- 制作面不消耗回合。
- 隐藏风味（special_feeling）通过固定回合和友人出行获取，上限 4。
- 隐藏风味可替代 0-2 个任意诀窍点。
- 诀窍和隐藏风味都有数量上限。
- 普通非比赛回合至多使用 1 种面。
- 拉面为当前回合提供基础效果 + 地区效果叠加的 Buff。

剧本专用状态应至少能表达：

```text
三种诀窍库存及获取顺序队列
三种诀窍槽（A/B/C）当前值
隐藏风味库存
当年已选择的三种地区拉面
当前回合使用的拉面及生效状态
剧本 Pt 及当年内吃面次数
剧本 Flag、计数器和持续状态
72-77 回合自动超级拉面状态
```

配方、面种类和效果属于拉面杯固定机制，原则上直接固化在 `scenario/ramen`，不放入通用用户配置文件。

### 3.2 组合动作

“做面和吃面”是一个动作；决策应视为完整组合：

```text
不吃面 + A 训练
吃面 X + B 训练
不吃面 + 比赛
吃面 Y + 休息/外出等非训练选项
```

核心规则层必须生成所有合法组合动作，不能因为面主要增强训练，就提前过滤“吃面 + 非训练”。策略层可以根据收益和启发式降低其优先级或剪枝，但不能让规则层失去表达能力。

推荐概念模型：

```text
RamenAction {
    ramen: Option<RamenType>,
    operation: Operation,
}

Operation {
    Train(TrainingType),
    Race(RaceId),
    Rest,
    Outing(OutingType),
    Clinic,
}
```

动作应用必须具有原子性：检查合法性、制作并消耗诀窍、消费面、应用回合 Buff、执行基础操作，任一步失败都不能产生部分状态变更。

### 3.3 年度选面与自动拉面

每年年初有独立决策：选择 3 种特定的面，之后该年度只能使用这 3 种面中的一种。前期先使用固定顺序策略，接口应允许未来替换为手写策略、搜索策略或强化学习策略。

72-77 回合存在自动生效的特殊超级拉面（finals_effect）：

- 自动生效。
- 不需要用户选择。
- 不应进入普通“吃面/不吃面”候选动作。
- 其效果应复用统一的状态效果应用路径，而不单独制造一套 Buff 系统。

### 3.4 动态规则能力

新核心必须允许剧本规则决定数值上限和效果语义：

- 体力可能超过默认 100 上限。
- 单次训练属性上限可能被 Buff 动态提高。
- 训练值应分阶段计算：基础值、加成、动态上限、截断/溢出、最终效果。
- Buff 可能提高特定训练上限、增加指定训练的分身 Person、提供额外 Hint、降低失败率等。
- Flag 不应全部建模为 `bool`，至少区分布尔状态、计数器、持续回合状态、数值状态和枚举状态。
- 事件需要支持条件、概率、选项、效果、优先级、次数限制、延迟触发和 Flag 更新。

## 4. Complexity Boundaries

### 4.1 固化范围

以下内容直接固化在拉面杯剧本模块中：

- 剧本名称、回合流程和阶段。
- 三种诀窍、配方和数量上限。
- 面种类、面库存和固定效果。
- 年度选面规则。
- 72-77 回合超级拉面规则。
- 拉面杯事件、Flag 和规则特判。
- 拉面杯专用状态、动作和静态数据类型。

不为这些内容建立通用配置表、动态注册表或脚本解释器，除非实际资料表明规则需要运行时修改。

### 4.2 复用范围

适度抽象以下真正稳定且有价值的公共能力：

- 游戏阶段推进和完整局面运行模板。
- 结构化决策请求和决策结果。
- 动作合法性、应用和预览的边界。
- 随机数和模拟上下文管理。
- 结构化游戏事件、回合统计和结果汇总。
- 诊断日志与用户展示的输出边界。
- 搜索配置、搜索统计、批量模拟接口。
- 用户配置、开发者默认配置和命令行覆盖的加载流程。
- 外部协议到剧本状态的适配边界。

### 4.3 明确避免的极端

不要把每个剧本的资源、Buff、事件和规则都抽象为通用 ID、注册表、动态 Trait 对象或配置脚本。也不要把拉面字段、温泉字段等剧本状态放进一个“万能 GameState”。

核心接口通过关联类型或清晰的泛型边界关联剧本，剧本自身拥有专用状态和动作。公共 crate 是否拆出，必须在依赖边界整理后根据真实共享类型决定，而不是为了形式上的复用提前拆分。

## 5. Proposed Changes

以下阶段是开发顺序，不要求一次提交完成。每一阶段完成后应保持可编译，并通过对应验证。

### Phase 0：资料收集与规则基线（最高优先级）

**目标**：用拉面杯实际机制反推最小领域模型，避免接口先于规则定型。

**需要整理的资料**：

- 略，人工整理
- 后续实现需要严格遵守这一步整理的游戏规则

### Phase 1：实现拉面杯核心模块（原 Phase 1 + 4 + 5 + 6 合并）

**目标**：直接在 `game/ramen/` 模块中实现拉面杯完整游戏逻辑，跑通最小闭环。由于拉面杯机制已明确，不先做抽象接口设计，而是从具体实现中自然提取通用部分。

**策略说明**：规则、预览、闭环紧密耦合，分开做会导致反复修改接口。因此将原计划中的 Phase 1（接口）、Phase 4（规则）、Phase 5（预览）、Phase 6（闭环）合并为一个连续阶段，分 4 个子步骤执行。

---

#### 1a - 建立 ramen 模块并定义核心类型

**模块结构**（位于 `crates/umasim/src/game/ramen/`）：

```text
mod.rs      -- 模块入口、RamenStage 枚举
state.rs    -- RamenGame 结构体（含 BaseGame + 拉面杯特有状态）
action.rs   -- RamenAction 枚举（含组合动作逻辑）
rules.rs    -- 核心规则（诀窍系统、做面/吃面、RMJ 结算、分身等）
effects.rs  -- 效果计算（基础效果、地区效果、超级拉面效果叠加）
events.rs   -- 剧本事件处理（含友人事件）
policy.rs   -- 手写策略（含地区选择、超级拉面选择）
```

**核心类型定义**：

```text
RamenGame       包含 BaseGame + 拉面杯专用状态
RamenAction     吃面/不吃面 + 基础操作的组合动作
RamenStage      普通回合 | 地区选择 | 超级拉面选择
RamenState      诀窍库存、诀窍槽、隐藏风味、剧本 Pt 等
RamenEffect     基础效果、地区效果、超级拉面效果的合并
```

**设计要求**：

- 通过 `Game` trait 实现，不直接依赖具体剧本字段以外的通用接口。
- `RamenAction` 用一个动作表达"吃面 + 基础操作"。
- 年度地区选择作为独立阶段，不塞入普通回合动作。
- 超级拉面选择初期固定为选项二（第二个 `training_limit_options`），不做独立决策。
- 通过 `Result` 表达边界错误。

---

#### 1b - 实现核心游戏机制

**诀窍系统**：
- 三种诀窍（A/B/C）库存管理，上限 10，维护获得顺序队列。
- 诀窍槽（A/B/C）系统，每回合填充，满 7 清零 + 1 诀窍。
- 基础值分配算法：按年度三个地区配方的诀窍消耗比例分配。
- 训练额外加成：`1 + 支援卡数量 + floor(NPC 数量 / 2)`。
  - 每回合每个训练随机分配一个诀窍类型角标（A/B/C），该角标决定训练额外加成作用于哪个诀窍槽。
  - 角标分配在 Person 分布完成后进行，与 Person 分布独立。
  - 需要在训练状态或回合上下文中增加字段存储该角标。
- 友情训练时三种诀窍槽各 +2（上限 7）。

**做面/吃面**：
- 消耗 5 个诀窍点（按地区配方比例），隐藏风味可替代 0-2 个。
- 仅当回合生效，效果为基础效果 + 地区效果叠加。
- 剧本 Pt 获取：基础值 + 叠加增量（当年内最多叠加 5 次，下年重置）。

**地区选择**：
- 每年年初选择 3 个地区，范围：第 1 年 id 0-4，第 2 年 id 5-9，第 3 年 id 10-19。
- 前期使用固定顺序策略。

**RMJ 结算**：
- 回合 23/47/71 结束时检查剧本 Pt 阈值（1500/3000/3500，第三年 5000 为大成功）。
- 成功/失败影响下一年常驻效果和训练等级剧本加成。

**超级拉面（72-77 回合）**：
- 自动生效，不需要用户选择。
- 不进入普通"吃面/不吃面"候选动作。
- 效果复用统一状态效果应用路径。

**分身系统**：
- 地区拉面分身：id >= 5 的地区效果，随机分配，不计算得意率，不包含友人卡。
- 超级拉面分身：每个支援卡固定额外出现一次，计算得意率，包含友人卡。

**友人系统**：
- 登场 → 点击 → 解锁 → 出行（5 次），按友人事件链触发。

**合宿**：
- 回合 36-39 和 60-63，训练等级均为 5，特殊事件触发。

**NPC 系统**：
- 5 个固定 NPC（美妙/怒涛/内恰/成田路/金镇），仅影响训练人数。

---

#### 1c - 实现动作预览和手写策略

- `list_actions`：生成所有合法组合动作（吃面/不吃面 + 基础操作），规则层不剪枝。
- `preview_action`：与真实执行使用相同规则路径，返回状态、资源、效果和事件的预测结果。
- 回合上下文缓存：基础训练值、人头分布、失败率、可用面和静态效果。
- 手写策略：基于收益排序和安全剪枝，不含复杂搜索。
- 地区选择策略：固定顺序（初期简单实现）。
- 超级拉面选择：初期固定选择选项二，不实现独立决策。

---

#### 1d - 跑通最小闭环

完整回合流程 0-77：

```text
初始化
    → 回合 0-1：基础训练（无剧本机制）
    → 第 1 回合结束：地区选择阶段
    → 第 2 回合开始：剧本机制初始化
    → 普通回合：诀窍槽填充 → 生成组合动作 → 策略选择 → 动作应用 → 事件处理
    → 回合 23/47/71 结束：RMJ 结算
    → 回合 36-39/60-63：夏合宿
    → 回合 71 结束：超级拉面选择
    → 回合 72-77：超级拉面自动生效
    → 回合 77 结束：育成结束
    → 终局结果和统计
```

**增量测试策略**（每步完成后立即添加测试）：
- 1b 完成后：诀窍系统、诀窍槽算法、做面消耗、配方匹配、RMJ 结算。
- 1c 完成后：动作生成、预览与执行一致性。
- 1d 完成后：完整回合流程、地区选择、终局结果。

### Phase 2：配置系统整理

**目标**：保留用户配置和开发者配置，但让业务代码只接收类型化运行时配置。

**涉及文件**：

- `crates/umasim/src/gamedata/config.rs`
- `crates/umasim/src/utils.rs`
- `game_config.toml`
- `gamedata/default_config.toml`
- 各二进制入口和 `umaai` 启动配置路径

**方案**：

```text
开发者默认配置
    -> 用户配置覆盖
    -> 命令行参数覆盖
    -> 类型化 RuntimeConfig
```

拆分职责：

- `SimulationConfig`：局数、剧本输入、数据路径。
- `SearchConfig`：搜索次数、深度、UCB、leaf evaluator 等。
- `PolicyConfig`：手写策略、未来模型策略参数。
- `OutputConfig`：用户展示、统计级别、诊断日志、文件输出。
- `DeveloperConfig`：调试、性能分析和实验开关。

拉面杯固定配方和规则不放进用户配置。清理旧 `OnsenOrder`、旧剧本名称和无效覆盖字段时，必须先确认所有入口迁移完成。

配置加载应集中处理相对路径、缺省值、覆盖规则和校验，业务模块不得自行读取 TOML 文件或依赖当前工作目录。

### Phase 3：结构化输出、日志和统计

**目标**：从数据模型上分离用户信息、程序诊断和分析统计。

**建议模型**：

```text
DiagnosticLog  开发者日志，可关闭、采样和分级
GameEvent      游戏过程事件，可回放/汇总/转 UI
GameView       面向用户展示的当前状态、推荐和结果
TurnSnapshot   每回合分析记录
GameResult     最终结果和汇总
```

`TurnSnapshot` 至少包括：

- 回合、阶段和决策类型。
- 训练前后状态。
- 诀窍、隐藏风味、面库存和当前 Buff。
- 可用候选动作。
- 每个候选的面、基础操作、预览收益、失败率、资源变化和被选状态。
- 最终选择及状态变化。
- 事件、Flag 和随机结果摘要。

统计收集级别：

```text
None        不收集回合细节
Summary     只收集最终结果和汇总
Turn        收集每回合状态
Detailed    收集所有候选动作评估
```

多线程 worker 不直接输出用户界面或普通日志；worker 返回结构化结果，由主线程或专用聚合器统一输出。搜索 rollout 默认静默，不依赖全局 `disable_log` 作为唯一手段。

**输出方向调整**：本项目交互模式更接近 AI 助手信息流，而非传统 TUI。结构化数据（`GameEvent`、`GameView`、`TurnSnapshot`等）的主要消费者是 AI 分析层和外部协议，由 `umaai` 等上层模块将结构化结果转化为自然语言推荐或协议响应。核心逻辑不直接依赖任何终端 UI 框架。`ratatui` 等终端 UI 方案不再作为默认输出方向，未来如有交互需求应优先考虑 AI 助手接口模式。

### Phase 4：整理 crate 边界

**目标**：先治理依赖，再决定是否新增公共 crate。

当前方向：

```text
公共稳定接口/基础类型 crate（是否新增待评估）
        ↑
     umasim
        ↑
     umaai / analyzer
```

先检查并消除：

- `umaai` 直接构造旧剧本内部状态的依赖。
- `analyzer` 对旧温泉类型的直接依赖。
- 搜索器对具体剧本的绑定。
- 配置、统计和决策类型在多个 crate 间重复定义。

只有确认某些类型同时被 `umasim`、`umaai` 和 `analyzer` 使用，且生命周期和语义稳定后，才提取公共 crate。公共 crate 不放拉面杯规则、搜索内部实现或外部文件监控。

### Phase 5：批量模拟和性能优化

**目标**：在规则正确、接口稳定后提高大量局面生成速度。

前置约束：

- 模拟核心默认不产生日志。
- 用户展示、诊断日志和统计可独立关闭。
- 静态数据与可变状态分离。
- 单局运行和批量模拟接口分离。
- 搜索复制的状态尽量紧凑，避免复制静态数据。
- RNG 由模拟上下文管理。

优化顺序：

1. 建立基准：单回合动作生成、单次预览、单局模拟、整次搜索、批量模拟。
2. Rayon `map_init` 复用 worker RNG，确认并行策略和结果可复现性要求。
3. 移除 rollout 用户输出和不必要的诊断路径。
4. 通过回合上下文缓存减少重复计算。
5. 优化动作生成和状态复制，必要时拆分静态数据与可变状态。
6. 评估轻量 rollout evaluator、动态搜索预算和 `max_depth + leaf eval`。
7. 在模型和数据成熟后再推进 GPU/ONNX 推理，沿用旧 GPU 规划中的 CPU 局面生成、批量 leaf eval 和模型训练方向。

每项优化都需要对比搜索质量、最终分数分布、统计正确性和线程安全，不能只看耗时。

### Phase 6：停止并删除温泉杯代码

**目标**：在新核心最小闭环和拉面杯主要逻辑稳定后清理旧实现。

先停止依赖：

- 新核心不引用 `OnsenGame`、`OnsenAction` 和温泉阶段。
- 新 `umaai` 协议适配拉面杯状态，不再构造温泉状态。
- `analyzer` 和二进制入口迁移到新剧本。
- 搜索、训练数据和统计不再依赖温泉动作编码。

再删除 `main` 分支中的：

- 温泉剧本状态、动作、阶段和数据。
- 温泉专用搜索/训练分支。
- 温泉配置字段和旧入口。
- 只服务温泉杯的特征、事件和工具。

删除前保留必要的规则对照资料、测试样例和迁移记录；完整旧实现继续由 `onsen_backup` 保存。

## 6. Verification Strategy

### 6.1 架构与编译

- workspace 全部 crate 可编译。
- 新核心不依赖温泉模块。
- `umaai`、`analyzer` 的依赖方向符合设计。
- 配置加载、默认值、用户覆盖和命令行覆盖可单独测试。
- 运行时不要求业务模块自行读取配置文件或依赖隐含当前目录。

### 6.2 规则正确性

为拉面杯添加至少以下测试类别：

- 诀窍获取、上限和溢出。
- 隐藏风味替代和配方消耗。
- 制作面不消耗回合。
- 年度三种面限制。
- 普通回合至多使用一种面。
- 比赛回合和其他操作的吃面合法性。
- 吃面 + 非训练操作的合法性。
- 组合动作原子性和非法动作不产生部分修改。
- 动态体力上限和训练单次上限。
- Buff 对训练上限、分身、Hint、失败率的影响。
- Flag 的设置、持续、计数和清理。
- 事件条件、概率、选项和延迟效果。
- 72-77 回合超级拉面自动生效不进入普通选择。

测试应优先输出清晰的状态和结果，避免用 `assert` 掩盖需要观察的模拟内容；关键状态转移应同时保留机器可验证的结果。

### 6.3 输出和统计

- 搜索静默模式不产生用户游戏信息。
- 诊断日志关闭时不影响游戏结果。
- 多线程模拟不会交错写入用户展示。
- `None`、`Summary`、`Turn`、`Detailed` 四种统计级别行为明确。
- 回合快照能还原动作候选、最终选择和状态变化。
- 统计数据可用于后续选择原因分析，而不依赖解析文本日志。

### 6.4 性能

建立固定基准并记录：

- 动作生成耗时和候选数量。
- 每回合预览耗时。
- 单局模拟吞吐量。
- 不同统计级别的额外成本。
- 单线程和多线程搜索吞吐量。
- 状态 clone/复制成本。
- 搜索结果质量和最终分数分布。

性能优化必须与旧实现或基准版本做行为对照，尤其是随机规则、动作合法性和搜索结果。

## 7. Assumptions & Decisions

1. `main` 是新开发主线，`onsen_backup` 是旧代码归档，不通过兼容层继续支持温泉杯。
2. 拉面杯固定机制优先使用剧本专用结构和代码固化，不做通用剧本配置化。
3. 通用层只复用稳定的流程和基础设施，不抽象所有资源、Buff 和事件。
4. 资料不明确的规则必须先标记为待确认，不通过默认值静默猜测。
5. 输出方向为 AI 助手信息流，结构化数据（`GameEvent`、`GameView`、`TurnSnapshot`）由 AI 分析层消费，核心逻辑不依赖终端 UI 框架。
6. 搜索 rollout 默认无用户日志，结构化统计按级别控制。
7. 组合动作是拉面杯动作空间的基本单位；年度地区选择是独立阶段；超级拉面选择初期固定为选项二，不做独立决策。
8. 前期年初选面采用固定顺序策略，未来通过稳定决策接口接入强化学习。
9. 公共 crate 是否新增不预先决定，以实际依赖图和稳定公共类型为依据。
10. GPU 加速和神经网络训练不是新剧本最小闭环的前置条件，但核心接口必须保留后续接入空间。
