## 1. 路线与目标

### 1.1 迭代路线（两代封顶）

```
手写策略(UA1-UA5)  +  扁平 MCTS   →  第一代教师数据  →  第一代网络 (policy + value)
第一代网络 policy  +  扁平 MCTS   →  第二代教师数据  →  第二代网络
```

第二代之后停止。上游经验：三代以上边际收益很小，计算成本却成倍增长。

### 1.2 为什么第二代能超过第一代

两条独立的增益来源，缺一不可：

1. **rollout 质量**：第一代 rollout 用手写策略，第二代用网络 policy。rollout 越强，
   搜索给出的动作价值估计越接近真实值。
2. **搜索提速**：第一代必须 rollout 到终局（贵）；第二代可用网络 value 头在中途截断
   （`max_depth > 0` + leaf eval），单位算力能跑更多次搜索，标签噪声更低。

**推论：value 头必须在第一代就一起训练**，否则第二代没有提速手段，迭代跑不动。

### 1.3 手写策略的定位与验收线

本项目**不追求手写策略接近人类高手**，只要求它「不误用剧本机制」。

| | 分数 | 评级 |
|---|---|---|
| 随机基线 | 31024 | UE |
| 当前手写策略 | **50900**（100 局×3 组种子：50833 / 50872 / 51001；第 4 组 200 局：50625） | **UB3** |
| **验收目标** | **≥ 55900** | **UA1** |
| （参考）UA5 上限 | 59999 | UA5 |

差距 **≈ +5000 分（+9.8%）**。

> **噪声底限（实测）**：100 局下 std ≈ 2200–2540，均值标准误 ≈ **240 分**；
> 三组互不相交的种子集测得的均值极差为 **168 分**；补测第 4 组（seed 777+，200 局）得
> mean=50625 / std=2358，四组极差 **376 分**。
> **因此单次 100 局对比中，小于约 500 分的差异不可信。**
> 迭代调参必须配合：(a) 固定的 held-out 种子集做最终验收，避免对训练种子集过拟合；
> (b) 多马娘 / 多卡组验收，避免对单一配置过拟合。

> **已确认**：该线针对**手写策略单独跑**（不含 MCTS）。
> 55900 是**目标线，不是准入门槛**——Phase 0 不阻塞 Phase 1/2，二者互不冲突，可并行推进。
> 真正的截止点在 **Phase 3 开跑之前**：教师数据一旦生成，rollout 用的就是当时的手写策略，
> 之后再提升手写策略也无法回溯修正已落盘的标签（见 §7.1）。

`search_n` 的语义是**每候选**，不是每决策点的总额，读上表时注意这一点。

| 项 | 值 |
|---|---|
| `search_n`（每候选） | **1024** |
| 10 万样本基础机时（24 线程） | **≈ 16 h** |
| 第 3 年 `RegionSelect` 放大 | **×1.14**（见下） |
| **实际预算** | **≈ 18 h** |

**第 3 年 `RegionSelect` 的放大系数**：采数据时该决策点必须跑
`ramen_region_strategy = all`（120 个候选组合）而不是 `fixed`，否则只有单候选、
搜索给不出分布；一条这样的样本成本 ≈ 普通样本的 **12 倍**
（见 [`policy_schema::REGION_SELECT_BASE`](../../crates/umasim/src/game/ramen/policy_schema.rs)）。
而 `sampler` 的截断回合是 `U(0, 77)`，第 3 年地区选择只落在 **1 个回合**上：

```text
样本占比   = 1/78                    ≈ 1.3%
机时占比   = 1×12 / (1×12 + 77×1)    ≈ 13.5%
总预算倍率 = (1×12 + 77×1) / 78      ≈ 1.14x
```

第 1、2 年的地区选择是 C(5,3)=10 个组合，与普通决策点同量级，不单独计。

**若嫌 13.5% 的机时不值**，正确做法是给 `RegionSelect` 设**独立采样配额**，
而不是靠 `U(0, 77)` 去撞——但第一代已拍板把地区选择纳入网络（见 §6.3 修订），
故本预算按纳入计。

##### ⚠ 上面这段推导的前提已于 2026-08-30 修正

「靠 `U(0, 77)` 去撞」撞不到想要的量：第 2/3 年地区选择在 turn 23/47 的**回合末**，
同回合的 `RamenSelect` / `Train` 通常先命中采样白名单把样本截走。
实测 1200 次自由采样（见 `sampler::tests::test_region_select_undersampled_without_quota`）：

```text
turn 2  （第 1 年）  7 条
turn 23 （第 2 年）  0 条     ← 全部被同回合决策点截走
turn 47 （第 3 年）  9 条     ← 占捕获样本 0.76%，只在前面决策点恰好不合格时才轮到
```

所以 ×1.14 的**量级**没错（假设 1.3%，实测 0.76%），但它不受控，且第 2 年归零。
真正的问题不是预算算错，是「第 3 年只有 ~9/1200 条样本」学不出 120 个组合的排序。

修复后（`SamplerConfig::region_quota_permille`，见 §6.5）配额是显式参数，
预算随之改为线性可算：

```text
总预算倍率 = 1 + q3 × (12 - 1)      q3 = 第 3 年地区样本占比
q3 = 1%   → 1.11x → ≈ 18 h
q3 = 3%   → 1.33x → ≈ 21 h   ← 现行默认（30‰）
q3 = 5%   → 1.55x → ≈ 25 h
```

第 2 年配额（默认 20‰）是 C(5,3)=10 个组合，与普通决策点同量级，不计入放大。
`q3` 取多少取决于组合头要学到什么程度（§6.4 未决），先按 3% 排预算。

### 2.2 未解释的性能差距

上游声称模拟器可达 **5000 局/s/线程**，实测拉面为 676 局/s，差 **7.4 倍**。

可能原因（未验证）：
- 拉面剧本本身更重（78 回合 × 三阶段状态机 + 事件系统）；
- Rust 移植的堆分配开销 —— 嫌疑点：`Game::list_turn_events` 每回合对每个候选事件
  `clone()`；`game.clone()` 中 `distribution: Vec<Vec<i32>>` 是嵌套堆分配，每次 rollout
  复制根状态都要走一遍；
- 上游数字本身偏乐观或对应更简单的剧本。

该差距对数据生成预算是**乘性**的，建议单独安排一次 profiling（见 Phase 0.5）。

### 3.2 主力模型 `Model_EncoderMlpSimple`（注册名 `"ems"`）

```
输入 [B, 1121]
  ├─ global  [B, 587]        → 2 层 embedding
  └─ cards   [B, 6, 89]      → embedding
        ↓
  堆叠 EncoderLayerSimple × encoderB   （对 6 张卡做 self-attention）
        ↓
  沿卡片维度 mean pooling
        ↓
  ResNet 风格 MLP trunk × mlpB（宽度 mlpF）
        ↓
  单个 Linear(mlpF → Game_Output_C)     ← 单头输出，切片得到 policy / value
```

注意力实现（简化版，**无 softmax、无多头**）：

```
att = relu(bmm(x, q.transpose(1,2))) / seq_len
y   = bmm(att, v)
```

模型注册表：`{"res", "tf", "tl", "lin", "ems", "ems2", "emsf", "emsm"}`，`ems` 为主力。

### 3.3 损失函数与训练超参

**policy**：对软标签的 KL 散度（交叉熵减去标签自身的熵，使 loss 下界为 0）

```
loss = -Σ log_softmax(output) * target + Σ log(target) * target
```

**value**：3 路 Huber，各自手工归一化

| 分量 | 归一化 | 权重 |
|---|---|---|
| `value[0]` scoreMean | `(label - 38000) / 300` | 0.2 |
| `value[1]` scoreStdev | `label / 150` | 0.4 |
| `value[2]` weightedMean | `(label - 38000) / 300` | 0.2 |

> **`38000` 是上游剧本的分数中心，拉面必须重新标定。** 当前手写策略均分 51168，
> MCTS 加持后更高，且随机卡组会显著展宽分布。该常数需由实际数据分布确定。

**优化器**：Adam。transformer 系 `lr=5e-4, wd=2e-5`；输出头单独用更低 lr。
batch size 1024。`valuesampling` 参数控制 value loss 的随机参与概率。

### 3.4 数据格式

上游 `dataset.py` 读 **`.npz`**，内含两个数组 `"x"`（输入）与 `"label"`（标签），
`float32`，**整个文件载入内存，不分片**。

本仓库 `collector.rs` 写 bincode 分片 `part_*.bin` + manifest，**比上游更完善**
（可断点续跑、有文件签名与 git commit 记录）。需补一个 `bincode → npz` 转换脚本。

#### 2026-08-29 修订说明

上表的「🔧 泛型化复用」在 Phase 1.4 完成后已过期，本次改为实际状态。两处需要展开：

**`training_sample.rs` 是温泉硬编码，不是「改个常数」那么简单。**
[training_sample.rs:17](../../crates/umasim/src/training_sample.rs) 起的
`NN_INPUT_DIM = 1121` / `NN_GLOBAL_DIM = 587` / `NN_CARD_DIM = 89` /
`NN_OUTPUT_DIM = 61` / `POLICY_DIM = 50` / `CHOICE_DIM = 8` / `VALUE_DIM = 3`
全部是上游温泉口径。拉面对应的是
`features::INPUT_DIM`（`GLOBAL_DIM + 6×CARD_DIM + 13×PERSON_DIM`）与
`policy_schema::POLICY_DIM = 234`，输出维度应为 `234 + 8 + 3 = 245`。

**取「拉面单开一份」而非「泛型化」**：温泉那条 NN 链从未闭环
（§6.4：仓库没有任何训练代码，也没有 `.onnx` 模型），为死链做泛型是给死代码交税；
且落盘格式是要冻结的东西，中间抽象层越少越好。

**写拉面版 `export_sample` 时不要沿用温泉实现的两个已知缺陷**（见 §9C 硬伤表）：
`policy_delta = 0` 时除零出 `NaN`；`action_to_global_index` 失败时该动作不写入
policy 向量、softmax 分母却仍然含它（概率泄漏）。新写正好绕开。

### 4.2 `extract_nn_features` 弃用理由

1. **手工维护扁平偏移量且无校验**：全靠 `idx += N` 累加推进，布局只存在于注释，
   函数末尾无 `assert_eq!(idx, NN_INPUT_DIM)`。任一段维度改动会导致后续全体错位，
   而特征错位不会让训练报错，只会让网络永远学不好。
2. **归一化常数错误**：`five_status[i] / 50.0`，而五维属性实际可达 1200+，
   结果是把输入放大到 24 倍而非归一化。`status_pt / 10.0` 等同样是无依据的魔数。
3. **静默吞错**：`if let Ok(..) = calc_training_buff(..)` 失败时留 0 不报错，
   「计算失败」与「收益为 0」在特征中不可区分；亦违反项目 Result 优先规范。
4. **把手写估值当特征**：温泉效果价值用 `vital*2.0 + youqing.sum() + ...*0.5 + ...*20.0`
   这样的手工加权分喂入网络，等于把手写策略的偏见硬编码进输入表示，
   与「喂原始状态、让网络自己学」的原则相反，且系数一改就要重生成全部数据。
5. **死维度占比高**：6 维搜索参数预留、6 维末尾预留、50 维动作掩码、78 维比赛回合标记。
6. **位置不当**：作为方法挂在 1845 行的 `onsen/game.rs` 内，无法单测。

**重写时保留 `TrainingSample` 容器结构，只换编码逻辑与维度常数。**

## 5. 分阶段计划

### Phase 0 — 手写策略提升至 UA1（51168 → ≥55900）

**定位不是调参提分，而是消除机制误用。** rollout 策略的系统性偏差会被搜索
放大并写进第一代标签（见 §7.1），因此必须先修掉已知的机制性错误：

- `failure_penalty`、`ramen_special_cost` 两个死参数（当前取值变化对结果无影响）；
- 第三年隐藏风味清空规则当前是反的（`select_special` 恒选最小隐藏风味用量）；
- 休息 / 外出的打分量纲与训练不可比（实测仅为训练分值的 1/100 量级，形同装饰）；
- PT 口径 `pt_rate = 8.0` vs 实际 `pt_score_rate = 2.0`；
- 智力训练的回体力被 `(-value.vital).max(0)` 截断为 0，未计入正收益。

**1.3 真 CRN：按 (turn, stage) 重播种（做成开关 + 实测）**

朴素「所有候选共用 `seeds[j]`」**只保证起始流位置相同，不等于 CRN**（见 §9C-CRN）。
对齐手段取「按阶段重播种」，搜索层内部即可完成，不改规则层：

```text
rollout j 开始:  rng = seed_from_u64(seeds[j])
apply_action(根动作, rng)
每次 next() 之后、run_stage 之前:
  rng = seed_from_u64(mix(seeds[j], turn, stage_id))
```

**必须先打配对相关日志 `corr(score_a, score_b)` 实测倍率，验证有效后才允许下调 `search_n`。**

##### 1.3 实测结果（2026-08-22，onsen / 回合 0 Train / 7 候选 / 每候选 200 rollout）

| 配置 | 平均配对 corr | 平均等效倍率 | 倍率区间 |
|---|---|---|---|
| 仅共享起始种子（1.1 的状态） | 0.1761 | **1.31x** | [0.99, 3.01] |
| 开启按 `(turn, stage)` 重播种 | 0.6922 | **3.65x** | [2.44, 8.62] |

倍率定义：`(Var_a + Var_b) / Var(X_a − X_b)`。独立抽样时为 1，配对生效则 > 1，
等价于把 `search_n` 放大同样倍数。

**两条结论**：

1. **朴素共享种子几乎没有收益（1.31x）**，实测证实了三方评审的修正——
   它只是可复现的独立抽样，不是 CRN。
2. **按阶段重播种确有效果（3.65x）**，且高于评审预估的 1.5–3 倍区间上沿。

**这个数字尚不能直接用于下调 `search_n`**，三点保留：

- 测在 **onsen** 上，目标剧本是**拉面**。拉面三阶段 / 合并决策会让状态分叉后
  策略路径差异更大，相关性预计更弱，**必须在拉面上重测**；
- 单一根局面、回合 0（rollout 最长、共享未来最多），后期回合收益应更低；
- 每候选仅 200 样本，倍率估计本身带噪。

倍率衡量的是**候选排序**的配对方差，不是绝对均值的估计精度——
用于 policy 标签正对口，但不能据此说「均值估得更准了」。

**默认值决策（2026-08-22）**：加开关时取默认 `false`，理由是当时**尚无实测数据**，
在无证据的情况下改变 `umaai` 实时通道层的行为没有依据。测得 3.65 倍后该理由失效，
故翻为 `true`，并同步暴露到 `[mcts] crn_stage_reseed` 供随时关闭。
翻转后重验：1 线程与 24 线程结果仍逐位相同（数值本身较关闭时不同属预期，随机流已改变）。

#### 1.4 完成记录（2026-08-22）

闭包注入从根上避免该陷阱：`search_with(rollout)` 是公共内核，
温泉 `search()` 在闭包里分发 `Dig`/`Upgrade`，拉面 `search()` 直接用 `simulate_common`。

**`fork_for_rollout` 取代了原计划的 `reseed_internal` 空实现**：把「克隆」与

规则层种子经 `InternalSeed` 与主种子分频道派生（同值即同一条流）。

### 6.5 落盘格式 —— **未冻结**（2026-08-30 审计结论）

> 先分清两件事：[`policy_schema.rs`](../../crates/umasim/src/game/ramen/policy_schema.rs)
> 冻的是**动作 ID 空间**（234 格），它仍然有效；本节讲的是**每条样本往磁盘写什么**，
> 这一层此前提出的「每候选 32 个 `u16` 分位数」方案**已否决，不要实现**。

#### 否决理由（逐条对着代码核实）

| # | 问题 | 证据 |
|---|---|---|
| 1 | `u16` 装不下分数 | [`result.rs`](../../crates/umasim/src/search/result.rs) 自己写死 `MAX_SCORE = 100000`，即代码库假设分数可达 10 万；`u16` 上限 65535，按均分 ~61600 算，1024 次 rollout 的高分尾必然溢出 |
| 2 | 两个统计口径本来就分叉 | `ActionResult::add` 的 `sum` / `sum_sq` 收原始 `f64`，直方图却走 `(score as usize).clamp(0, 99999)`——`mean()` 与 `weighted_mean()` 不在同一份数据上算 |
| 3 | 每候选缺 stdev | 改 `rf` 会换掉最优候选，只存 mean 无法重算 value 三元组 |
| 4 | 地区不是单格 | `slots_of` 对 `RegionSelect` 返回 `PolicySlots::Three`，一个格位 ID 描述不了组合 |
| 5 | 每候选有两套分布 | `action_results: Vec<(ActionResult, ActionResult)>`（score / score_pt） |

补充两条现场发现，都不是格式问题而是代码事实：

- **rollout 顺序在 `ActionResult` 层已经丢了**——它是直方图不是序列。所以「保留 CRN
  配对以后做配对 bootstrap」不是换序列化格式能拿到的，要在
  [`flat_search.rs`](../../crates/umasim/src/search/flat_search.rs) 的两个
  `ActionResult::new()` 旁边加一条按 rollout 序追加的 `Vec<f32>`。
- **稠密直方图的内存**：每个 `ActionResult` 是 `vec![0u32; 100000]` = 400 KB，
  每候选两份。第 3 年 `all` 策略 120 个候选 → 单次搜索单线程约 **96 MB**。
  开跑 Y3 前值得先量。

#### 拟采用（待实现，仍可改）

| 层 | 内容 |
|---|---|
| `features.f32` | `[N, 754]` 定长，直接 mmap |
| `sample_meta` | 每样本定长：turn / stage / index / 搜索根种子 |
| `candidate_offsets` | `N+1` 个 `u64`（CSR） |
| `candidates` | 变长：动作 ID（地区用 20-bit mask 或稳定组合 ID）+ 每候选 1024 个原始 `f32` 分（**按 rollout 序号定长槽位，见 §6.6**）+ 精确 `n / sum / sum_sq` |
| `labels/<hash>.f32` | 按某组 `rf / delta` 离线生成的定长 policy/value，**可再生 sidecar，不是权威字段** |

- **只冻结终局 score 轴**：`gamedata/default_config.toml` 是 `mcts_selection = "score"`，
  `score_pt` 不在活跃路径上。存储因此减半（≈ 8.2 GB / 10 万样本 × 20 候选），
  但**这一条必须写进契约**——不能事后声称「以后还能换评分口径」。
- **存 `f32` 而不是 `u32`**：分数是 `f64` 且非整数，`u32` 逼你现在就定舍入规则；
  `f32` 同为 4 字节、在 2²⁴ 以内对整数无损，把这个决定推后。
- 训练热路径只 mmap `features + labels`；变长候选表仅在生成某组超参的标签时顺序扫一次。

#### 尚未回答的两个问题（开跑前必须定）

1. **标签口径**：离线标签生成器是**复刻现行语义**（整数截断 + 夹 99999），
   还是按原始 `f32` 无损重算？两者的 `weighted_mean` 不会逐位相同，
   而这是与历史基线对比的唯一锚点。倾向：复刻现行语义，同时输出无损版做审计。
2. **地区头 234 vs 354**：多热 top-3 只在组合价值近似可加时成立
   （`Q({A,B,C}) ≈ b + qA + qB + qC`），目前无证据。替代方案是给三年各开独立组合槽
   （Y1 10 + Y2 10 + Y3 120 = 140，总维度 354）。
   **在 Y3 pilot 数据到手前无法检验**，故 §6.3 的 234 维暂不动。

##### 采集链落地记录（2026-08-30）

三段都已接通，`sampler → search → export_ramen_sample → 分片 + manifest`。

- **有序 rollout**：开关默认关，关时不分配也不改变搜索结果（同种子下 `best_action_idx`
  与各候选 `mean()` 逐位相同）。失败的 rollout **留空不前移**，UCB 路径同样按序号写入
  ——这两点错了不会编译失败也不会测试变红，但会静默毁掉 CRN 配对。
  对齐由 `test_ordered_rollouts_align_with_crn_seeds` 钉死：让 rollout 闭包把种子当分数返回，
  于是有序行本身就是种子序列，可逐位对照 `seed_at(k)`，并带一条「错开一位能被发现」的反面对照。
- **manifest 记实际取值**：四条前提在 manifest 里是 `record_ordered_rollouts: true` /
  `use_ucb: false` / `radical_factor_max: 1.4` / `ramen_region_strategy: "all"` 这样的具体值，
  不是「已设置」。另存 7 个游戏数据文件的 FNV 签名 + git 提交 + 各分片签名。
- **续跑语义**：`--count` 是从 `--start` 起算的**累计目标**，不是增量。
  空区间会报错并保持 manifest 不变——早期版本会静默退出并把已完成任务的 `finished_at` 抹成 null。

##### 10 条 pilot 实测（2026-08-30，`search_n=1024`）

`--count 10 --search-n 1024`，默认配额 `[20, 30]`‰，未抽到 RegionSelect。

**速度**：10 条 18 秒，共 50 个「候选 × 1024 rollout」，即 **0.36 s / 候选**。
按本次候选构成（均值 5.0 个/条）外推 10 万条约 **50 机时**，
再加第 3 年 30‰ 的 120 候选样本（每条约 43 s，3000 条约 36 h），
合计 **约 84 机时**——是 §2.1 里 21 h 估计的 4 倍，那份估计需要重做。
落盘约 24.5 KB/条（Y3 样本 492 KB/条），10 万条含 Y3 约 **4 GB**，低于此前 8.2 GB 的估计。

| Train (turn 15) | 66.1 | 55.7 | **1.19** | 2.07x |
| Train (turn 51) | 57.5 | 41.1 | **1.40** | 1.81x |
| Train (turn 68) | 40.0 | 12.6 | 3.18 | 3.19x |
| Train (turn 41) | 165.1 | 40.6 | 4.06 | 1.86x |

##### 为什么「候选地区块」不做（2026-08-30 复核）

先前记的待办是「`encode_regions` 在地区未选出时整块填零 ⇒ RegionSelect 决策点上

- policy 的地区格位按**地区 ID** 编。两者相加 ⇒ 把候选效果喂进输入不带来新信息：
  网络在输出层为地区 i 学一组权重，与在输入层读第 i 块常量效果是同一件事。
- 真正随对局变化的是**当年已选中的 3 个地区**，那一块本来就在编。

### 6.6 rollout 顺序与 winner's curse（2026-08-30 外部评审 + 本地核实）

**拍板：现在付「保留 rollout 顺序」的代价，不付「改成半数选择/半数估值」的代价。
这两件事不绑在一起。**

#### 为什么现在必须保留顺序

理由不是 winner's curse 一定很大，而是**保存顺序的边际成本近乎为零，而重跑成本是十几机时**。

- 既然已决定落盘每候选 1024 个原始 `f32`，**有序与无序占的磁盘一样大**。
- 搜索期多出的内存：普通 20 候选 `20×1024×4 = 80 KB`；Y3 的 120 候选 480 KB。
  对比现在两个 10 万格稠密直方图在 Y3 就占约 96 MB —— 可忽略。
- 改动面只是**采集专用路径**在累加时另存一份有序结果，不动生产 MCTS 的公开语义。

⇒ 先展开直方图再落盘，等于主动丢掉几乎免费的信息。

#### 本地核实（都属实）

| 断言 | 核实 |
|---|---|
| 顺序丢在 `CandidateAccum::push` | 属实，`push` 直接 `self.score.add(...)` 进直方图 |
| `simulate_many` 本来就按 `k=0..n` 跑、各候选共享同一 `k` 与 CRN 种子 | 属实，`seeds.seed_at(offset + k)` |
| **失败 rollout 被跳过** ⇒ 一侧失败后候选间 CRN 对齐错位 | 属实，`Err` 分支只 `acc.failed += 1`，不占槽位 |
| `radical_factor_max` 配置陷阱 | 属实且是新的一条：`SearchConfig::default()` 是 **50**，而 `default_config.toml` / `game_config.toml` 都是 **1.4**。驱动忘了覆盖，`n_eff` 只剩约 40，winner's curse 从次要问题升级成严重问题 |

#### winner's curse 的量级（**估计，不是实测**）

对方按 CRN 实测相关性 `ρ≈0.7736`、等价值候选、近似正态给的上界：
选择偏差 ≈ `σ·sqrt((1-ρ)/n_eff)·E[max Z₁..Z_m]`，其中排名加权的有效样本数
`n_eff ≈ n·(2rf+1)/(rf+1)²`。`n=1024, rf∈[0,2]` 时约为 rollout 分标准差的
**20 候选 2.8–3.7% / 120 候选 3.8–5.1%**。

这是等价值候选的最坏模型上界，真实候选有价值差距通常会低于它；但后期 CRN 相关性
也可能低于回合 0 的实测值。**它是系统性正偏，不会因为样本多而自动消失。**
本表未经我们自己复算，当量级参考用，别当结论引。

#### 为什么不采用固定 512/512

半拆确实消掉了「同一噪声既选择又估值」，但它换了目标语义：选择只用 512 次而
policy 标签可能用全部 1024 次；value 估的是「512-rollout 搜索器所选动作」的价值
而非当前 1024-rollout 教师的价值；value 方差翻倍；policy 与 value 还可能指向不同的
best action。

**更好的默认实验是离线 4-fold / 8-fold cross-fitting**（原始有序分存下来后完全免费）：

1. 留一折作估值，用其余 3/4 或 7/8 的 rollout 选 best；
2. 在留出折上评估所选动作；合并各折留出结果生成 value；
3. policy 仍用全部 1024 条。

选择预算变成 768 / 896，更接近正式的 1024，且每条 rollout 都参与过一次独立估值。
先比 naive value 与 cross-fit value，再决定训练用哪个。

#### 两个必须一起处理的细节

- **不能只顺序 `push` 成功结果**：失败 rollout 一跳过，候选间的 CRN 对齐就错位。
  采集要么**遇到任一失败就丢弃整个根局面**，要么存 validity bitmap（按 rollout 序号定长槽位）。
- **所有候选必须用同一个 fold 划分函数**，例如 `fold = hash(root_seed, rollout_index) % K`，
  不许各自随机切。

#### 一个更根本、留给第二代的疑点

温泉现有 `export_sample` 的 value 是 best 候选的 `mean/stdev/weighted_mean`，确实有复用偏差；
但现有 NN 推理只读前两维（第三维被忽略），截断搜索甚至只消费 `score_mean`，而拉面目前
明确不支持截断 leaf。所以优先级是：

1. 现在保留有序原始 rollout，**保住后悔权**；
2. 不冻结任何半拆标签算法；
3. 用含 Y3 的小 pilot 比较 naive 与 4/8-fold value；
4. **在第二代接 leaf 之前**必须讲清 value 到底表示 `max_a Q(s,a)` 还是 rollout 基策的
   `Vπ(s)`——若是后者，就根本不该从 best 候选生成 value。

## 7. 风险

### 7.1 rollout 策略偏差（本路线的核心风险）

扁平 MC 中，动作 `a` 的价值是 `E[终局分 | 先执行 a，其后遵循 π_rollout]`。
**弱 π_rollout 会系统性低估「需要后续正确接手才能兑现」的动作。**

拉面的具体例子：攒诀窍 / 存隐藏风味以备后续大面，只有在 rollout 策略真的会用好它时
才有正收益；若 rollout 策略浪费掉，搜索就会学到「不要攒」——
这个错误结论会被写进第一代标签。

**缓解**：
- Phase 0 的验收线（UA1）正是为此设置 —— 不要求强，但要求不误用机制；
- 第二代用网络 policy 做 rollout，该偏差会自我修正，这正是迭代的意义；
- 教师数据中记录 rollout 策略版本号，便于事后归因。

### 7.2 第一代可能不及预期

若 Phase 4 的验收（纯网络 policy > 手写策略）未通过，可能原因排序：
标签噪声过大（`search_n` 不足 / 未开 CRN）→ 特征表示不足 → 局面分布覆盖不够
→ 网络容量或超参。应按此顺序排查，不要先动网络结构。

### 7.3 数据生成是长任务

10 万样本 5–35 小时。必须依赖 `collector.rs` 的断点续跑与 manifest，
中途不得修改 gamedata 或策略代码（manifest 会记录签名，事后可验证）。

| `crates/umasim/src/main.rs:352` | ✅ 在用。`trainer = "mcts"` 分支 |
| `crates/unused/bin/generate_mean_filtered_data.rs` | ❌ 死代码，`crates/unused` 不是 workspace member |
| onnx leaf eval 分支 | ❌ 未在用，已 cfg gate + 注释掉（无 .onnx 模型属实） |

**因此「回归面小」不成立**：真正没在用的只有 nn leaf eval 那一支，MCTS 搜索主体是温泉实时辅助 app 的核心链路。
A1 方案保留，但泛型化必须保证 onsen 路径行为不变。

**顺序调整（2026-08-22 定）**：原计划「泛型化 → CRN」改为 **「种子注入/CRN → 建 onsen 回归基准 → 泛型化」**。
理由：`flat_search.rs` 有 8 处 `StdRng::from_os_rng()`（190/218/256/267/305/312/370/376 行），
外部传入的 `rng: &mut StdRng` 在并行分支里被完全忽略——**当前搜索不可复现，
无法为泛型化建立「改动前后输出一致」的回归基准**。必须先修可复现性，才有回归保护可用。
CRN 本身也正是这件事的一部分（同一决策点各候选共享同一组 rollout 种子）。

#### §9C-CRN 三方评审结论（2026-08-22）

评审方：Codex(GPT-5.6) 与 Grok(4.6) 各自独立评审本仓库代码；另一路 Grok 取证上游 `hzyhhzy/UmaAi`。
**三方在以下各点独立得出一致结论**，故直接采纳。

##### 结论 1：种子分配取方案 A，候选索引禁止进入种子派生

- 方案 A：候选 i 的第 j 次 rollout 一律用 `seeds[j]`。
- 方案 B：`seed(i,j) = hash(root, i, j)`。**破坏 CRN，不予采用。**

依据：CRN 要的是配对样本，`Var(X_a - X_b) = Var X_a + Var X_b - 2 Cov(X_a, X_b)`。
只有 A 能把协方差做正；B 使 `Cov ≈ 0`，等于换回独立抽样。
B 只适合当并行任务的槽位索引，不能当共享随机种子的键。

派生方式沿用仓库既有约定 [`bench::seeded_rngs`](../../crates/umasim/src/bench.rs) 的
SplitMix64 黄金比例常数 `0x9E37_79B9_7F4A_7C15`，不另立一套。

##### 结论 2：⚠ 原判断修正 —— 共享种子序列 ≠ CRN

**「所有候选共用一条种子序列就等于做了 CRN」不成立。**
不同候选一执行状态立刻分叉，后续随机数消耗长度不同；共用 `seeds[j]`
只保证**起始流位置**相同，不保证第 t+1 回合抽的是同一件事。
顺序流一旦错位，配对甚至可能劣于独立抽样。

**不带对齐的方案 A 只是「可复现的独立抽样」，文档与提交信息中不得写成「已实现 CRN」。**

对齐手段的取舍：

| 手段 | 结论 |
|---|---|
| **按 (turn, stage) 重播种** | ✅ **采用**。搜索层内部即可完成，不改规则层，对齐的正是 CRN 大头（t+1 回合的人头分配） |
| Philox 等 counter-based RNG | ❌ 不进 Phase 1。仅当「可跳的顺序流」用**同样错位**；要有效必须把 `(turn, stream_id)` 编进 counter，等于给规则层每个随机点命名，代价远大于重播种 |
| 「多抽几下把消耗补齐」 | ❌ 动作一变就碎 |

###### ⚠ 上表只对 onsen 成立（2026-08-29 修订）

**拉面不走「按 (turn, stage) 重播种」这条路**，读本节时务必区分两个剧本，
否则会去修一个已经不存在的问题：

| 剧本 | CRN 载体 |
|---|---|
| **onsen** | `FlatSearch::reseed_for_stage`，受 `config.crn_stage_reseed` 开关控制 |
| **拉面** | 规则层已改为**无状态随机流**，`fork_for_rollout(rule_master)` 按 rollout 注入；<br>各候选第 `j` 次 rollout 共享 `seeds.seed_at(j)`，对齐由无状态流本身保证 |

[`flat_search.rs`](../../crates/umasim/src/search/flat_search.rs) 中 `reseed_for_stage`
的文档注释已写明「仅规则层未改造的剧本（onsen）使用……拉面 rollout 路径不再调用本方法」。
生产路径 `simulate_common(game, action, seed)` 把 `decision_seed` 与 `rule_master`
传同一个值，对照实验走 `simulate_common_with_seeds` 分开传。

**连带**：`audit_b_observability.md` 的 Bug 2（「拉面 CRN 测量工具是空跑」）**已修复**——
A/B 轴由 `crn_stage_reseed`（对拉面恒为空转）换成 `shared_rule_master ∈ {true, false}`，
独立臂给 `rule_master` 带上候选身份。2026-08-24 首次有效测量结果见下方修订表。
**红线**：不许为做对照去改 `seed_at` 或 `fork_for_rollout`——生产 CRN 是对的，错的是测试。

##### 结论 3：⚠ 「等效 4–10 倍 search_n」作废

原文的 4–10 倍是无实测支撑的预期值。Grok 给的经验区间是**加对齐后 1.5–3 倍**，
且手写策略会随状态分叉、相关性衰减。**工期估算不得押在此数上**；
必须先打 `corr(score_a, score_b)` 配对相关日志实测，验证后才允许下调 `search_n`。
`max_depth > 0` 时相关衰减更慢，CRN 更值——即第二代比第一代更受益。

##### 结论 4：Phase 1 回归与第一代标签一律用均匀分配

仓库当前 `use_ucb` 默认为 `true`（[config.rs](../../crates/umasim/src/search/config.rs)）。
UCB 的分配依赖分数，代码一改样本数就变，**不能作为回归基准的尺子**；
且 UCB 把样本堆给领先动作，对「找出 argmax」有利，对「产出整张 policy 分布」不利。
故 Phase 1 回归与第一代教师数据均强制 `use_ucb = false`。

UCB 下若要保留 CRN：动作 a 的第 k 次 rollout 用 `seeds[k]`（按**该动作自己的**次数索引，
不是全局调用次数），配对长度为 `min(n_a, n_b)`，多出部分为 unpaired——这是不等样本数下的标准做法。

##### 结论 5：规则层 RNG —— onsen 干净，ramen 是泛型化时的地雷

- **Onsen**：`grep internal_rng` 在 `game/onsen/` 下为空，`simulate()` 全程透传 `&mut StdRng`。
  修掉 8 处 `from_os_rng` 后即完全受控。
- **Ramen**：`RamenGame` 有第二条流 `internal_rng`（吃面落地分身、RMJ 事件走它；
  人头分配、训练失败、普通事件走传入 rng）。`take_internal_rng()` 在 `None` 时
  **回退 `from_os_rng()`**；而 `Clone` 会复制 RNG 状态——
  [`state.rs`](../../crates/umasim/src/game/ramen/state.rs) 的注释里**已写明搜索分叉需按分支重置**。

  泛型化时两种失效模式都要防：clone 出来是 `None` → 每次 rollout 自己摸 OS rng，搜索种子管不住规则层；
  root 已 `set_internal_rng` → 所有候选共享同一份后续内部流，形成意外的、错位的弱 CRN。
  **对策**：每个 rollout clone 之后用 `mix(seeds[j], INTERNAL_STREAM)` 注入 `set_internal_rng`。

##### 上游取证：CRN 是我们相对上游的增强，无样板可抄

上游 `MainAi.cpp` 整次运行只建一条 `mt19937_64`，候选之间**串行共用同一条流**——
动作 B 从动作 A 抽剩的位置接着抽。UCB 后搜的动作吃的是被前面候选抽残的流。
**上游没有 CRN，也不以可复现为目标**（线上 `random_device` 播种）。

其余可用结论：

| 项 | 上游做法 | 对我们的含义 |
|---|---|---|
| 剧本解耦 | **无抽象**，每剧本一个 git 分支整份复制 `Game`/`Action`/`Search` | 泛型化只能自己设计薄接口，无样板 |
| 搜索分配 | 只有 UCB，无均匀分配路径（早期 LArc 分支才是均匀） | 我们的 `use_ucb=false` 是自己加的，正好用作回归尺子 |
| `search_n` 语义 | 上游 `searchSingleMax` 是「最优动作停搜阈值」，非每动作定额 | 参数语义不同，勿直接对比数值 |
| 激进度 | 线上确定性公式 `sqrt(remain/TOTAL)*max`；随机抽仅用于 selfplay | 我们 `compute_radical_factor` 已对齐 ✅ |
| leaf 截断 | 注释说 NN 版 `maxDepth=10`，**线上实际默认搜到终局** | 「有 value 网就截断到 10」是设计不是现状，勿照抄 |
| NN 批推理 | lockstep：同深度整批同步步进，每 ply 一次推理 | 与我们「各自 rollout 再攒 leaf batch」形状不同，待第二代再议 |

**参数待办**：上游线上 `expectedSearchStdev` 为 2200（master）/1800（UAF），
而 [`default_config.toml`](../../gamedata/default_config.toml) 生效那节写的是 **15000.0**
（同文件另一节为 2200）。该值直接进 UCB 探索项，差 7 倍会显著改变搜索分配，需复核。

**已核实无需改动**：`ActionResult::compute_weighted_mean`
（[result.rs](../../crates/umasim/src/search/result.rs)）已正确移植上游的分位幂加权，
搜索排序走的是这条。`ValueOutput::with_radical_factor` 的 `mean + k*stdev` 仅用于 NN leaf，
且 onnx 路径当前未启用，不影响搜索排序口径。

### W3 — 进 Phase 1 之前

#### C4（新增，**须排在 C1 之前**）— 拉面 rollout 的规则层随机独立性

`RamenGame` 有 `internal_rng: Option<StdRng>`（`ramen/state.rs:171`），
而搜索的 rollout 是 `game.clone()`（`flat_search.rs:451`）。`StdRng: Clone`，
因此**同一根局面 clone 出的 n 次 rollout，规则层随机流可能完全相同**。
若成立，n 次 rollout 在规则层维度上只是 1 个有效样本，估值方差被严重低估，
`search_n` 加多少都无效。onsen 无此字段，该坑只在拉面接入时爆。

- 做法：从同一根 clone 20 次跑到终局，看终局分方差；再与「每次重新播种 `internal_rng`」对比。
- 判据：两者方差同量级 → 无事；前者显著偏小或为 0 → 这是搜索层的头号 bug，必须先修。
  修复若需动 `ramen/state.rs`，走提案模式（见 §8 未决 6）。
- 耗时：0.5 h。

#### C1 + C3（合并为同一套 harness）

在 Phase 1 泛型化完成后**直接在拉面上测**（决策 11）。

- 做法：固定 30 个局面（手写策略跑到随机回合 `t`）；
  `search_n ∈ {200, 500, 1000, 3000, 5000}` × `{CRN on, CRN off}` × 各重复 20 次；
  另跑一次 `search_n = 50000` 作金标准。
- 度量：(a) top-1 动作在 20 次重复中的众数占比；(b) 每候选估值在重复间的 std；
  (c) 与金标准的 top-1 一致率 / Kendall tau。
- 判据：**等效倍率 = CRN off 达到同等稳定性所需的 `search_n` ÷ CRN on 所需的 `search_n`**。
  <2 倍 → CRN 不划算，直接加 `search_n`；≥4 倍 → 按 §5 Phase 1 推进。
  C3 的取值（3000 还是 5000）由 (c) 曲线的拐点决定。
- 实现要点：规则层与决策层是两条独立 RNG 流，且**消耗量随动作分支变化**，做不到严格同步流。
  可行做法是「rollout 序号 `i` ↔ 固定 `seed_i` → 派生 `(decision_rng, internal_rng)`」，
  实现简单，收益取决于分歧速度 —— 所以必须实测。
- 耗时：实现 3 h + 机时 1–2 h（24 线程）。

#### D1 — `collector.rs` 断点续跑

- 做法：生成 500 样本 → 中途 kill → 重启 → 校验 manifest、分片总数、无重复无丢失。
  可在 onsen 链路上测（collector 与剧本无关）。
- 判据：续跑后样本总数正确且无重复；manifest 的签名校验能发现中途改动。
- 耗时：1 h。

### 13.2 首次闭环失败与归因

第一版模型闭环 **5873 分、自选比赛未达标 100%**，三年 `eat_count` 全 0。
Python/onnxruntime 复算证明 Rust 侧映射正确（回合 0 value 预测 65442，
手写实测 65438）。故障在模型：Train 阶段 10 个动作坍缩到 3 个，
「比赛」在 4566 次合法出现中被选中 **0** 次（教师 182 次）。

**根因（外部评审修正了我们的表述）**：不是策略改进定理失效，而是**信号密度**——
手写策略会替候选兜底，把「必须比赛」的价值压缩进极少数临近截止的状态。
硬数据：`remaining == need` 的严格截止状态**全库仅 3 条**；`remaining == need + 1`
仅 43 条。8 万条线性放大后也只有约 20 条，**不可能学出接近 100% 的规则可靠性**。

软标签不是成因：Train 标签平均熵 0.334（八动作均匀为 2.079）；比赛为最优的
182 条里比赛标签概率中位数 **0.795**、无一为零，而网络只给 0.038。

### 13.6 尚存差距与下一步

62246 vs 65438，缺口 **3192 分**（标准误 140，为确凿差距而非噪声）。
教师标签是 `greedy(Q^手写)`，按策略改进定理理论上应**优于**手写，
故该缺口是蒸馏损失，来源待定（数据量 / 训练 / 动作覆盖）。
8 万条数据到齐后为检验点。

待办：
- 动作类别重加权：外部评审的反事实显示宏召回 74.5%、比赛召回 68.4%，
  但平均 regret 由 57.1 回升至 64.8。需以闭环均分裁决该取舍。
  `train.py` 现仅有阶段权重、无动作权重。
- 离线预警指标（当前全缺，无任何离线量能预警闭环 100% 失败）：
  逐动作召回 + 宏召回 + 预测动作支持数；守门命中状态的强制动作召回（须 100%）；
  regret 的 P99 / max / top-1% CVaR（当前 Train 均值 151 但 max 29559、CVaR 2723）；
  RamenSelect 不吃面率。checkpoint 选择改为约束优先：
  硬约束违规为零 → 闭环均分 → 平均 regret。
- 第二代不应继续只蒸馏 `Q^手写`：以「Gen1 网络 + 守门」产生访问状态，
  并以该策略作为 rollout 接管策略做 DAgger / 重搜索，方能解闭环分布偏移。

产物：`saved_models/ramen_iter2_default/`、`saved_models/ramen_iter2_b256/`。

### 13.7 动作重加权：配对闭环否决（2026-08-30）

`train.py` 新增 `--train-action-reweight`（默认关闭）：仅对 Train 阶段的 policy KL
加权，类别取软标签在 10 个基础操作格中的 argmax，权重为训练集频率的逆平方根、
上限 4、归一化到均值 1；不重加权 value loss，不影响其他阶段。
实际权重 `[1.048, 0.920, 2.261, 2.797, 0.728, 2.359, 1.314, 2.367, 0.699, 2.797]`。

同参数（`--epochs 400 --batch-size 256 --head-lr 5e-4 --seed 20260830`）配对对照，
同 525 计划、同种子、同守门，各 4200 局：

| | 闭环均分 | 留出 regret |
|---|---:|---:|
| b256（无重加权） | **62239** | 57.6 |
| b256 + 重加权 | 62071 | 58.0 |

配对差 **+167.9**，配对标准差 3784，标准误 58.4，**t = +2.88（p ≈ 0.004）**。
**结论：不采纳重加权。**

选模规则（已定）：单次训练内部仍由平均 regret 选 `best.pt`；训练方案之间由
**配对闭环均分**裁决；宏召回仅作防坍缩诊断，不作选模信号——硬守门已消除比赛召回的
安全意义，宏召回把「偶尔错选无关紧要的稀有动作」与「漏掉关键动作」等量看待。

重加权确实兑现了防坍缩，但那不是瓶颈。五维终值：

| | 手写 | b256 | 重加权 |
|---|---:|---:|---:|
| 速 | 3128 | 3064 | 2945 |
| 耐 | 2128 | 1954 | 2159 |
| 力 | 1847 | 1382 | 1462 |
| 根 | 1424 | 1319 | 1485 |
| 智 | 1675 | 2144 | 1910 |
| gauge_overflow_y1 | 0.8 | 4.3 | 3.4 |

重加权把耐/根拉回甚至超过手写、智降下来，换来速度下滑，净亏 168。

### 13.8 数据量曲线（2026-08-30）—— 决定性结果

`train.py` 新增 `--max-train-samples`：按 `splitmix64(sample_id, seed)` 对训练引用
稳定排序后截断。三个性质：确定性；**同种子下各数据量点严格嵌套**（差异只来自数据量）；
按样本而非按 (马娘,卡组) 组合抽稀（与真实补数据同分布，避免组合覆盖度混淆）。
验证集不受影响，各点留出指标可比。抽稀哈希用训练种子，故多种子同时覆盖
「初始化差异」与「抽到哪批样本」两种方差。

4 个数据量点 × 3 种子，每个模型闭环 4200 局：

| 训练样本 | 闭环均分 | 种子 σ | 距手写 | 留出 regret | 三个种子 |
|---:|---:|---:|---:|---:|---|
| 3000 | 57401 | 1663 | −8037 | 77.1 | 58075 / 55507 / 58621 |
| 5000 | 58352 | 1381 | −7086 | 68.0 | 59835 / 57104 / 58116 |
| 8000 | 61345 | 286 | −4093 | 57.8 | 61496 / 61016 / 61524 |
| 10761（全量训练集） | **62569** | 671 | −2869 | 53.7 | 63075 / 61808 / 62823 |
| 手写基线 | 65438 | — | — | — | — |

**曲线完全没有走平。** 对 log₂(样本数) 线性拟合：**每翻倍 +2949 分，R² = 0.9507**。
种子散布随数据量收窄（1663 → 671），说明剩余差距以方差为主而非偏差——
**推翻了 §13.6「三条系统性偏差、更多数据未必补得上」的判断。**

外推（20000 → 65043 / 40000 → 67991 / 80000 → 70940），按此斜率
**约 21900 条追平手写**。

**外推的局限（必须记住）**：log 线性仅在 3.6 倍区间内拟合，外推到 7 倍很激进；
曲线必然在教师上限处弯折——理论天花板是 `greedy(Q^手写)`，按策略改进定理 ≥ 手写，
但高多少未知，几乎不可能到 70940。80k 的真实落点估计在 65000–68000。
稳的结论只有一条：**80k 足以追平并小幅超越手写。**

### 13.9 当前结论

1. **数据是唯一的主要瓶颈**。数据翻倍 +2949 分；超参调优（默认 → batch256 + head-lr 5e-4）
   只值 +2748 分（一次性）；动作重加权 −168 分。不应继续在 12k 上调优。
2. 等 Debian 第二批 7 万条（`--start 2100000 / 2200000`，各 36000），总量约 8.2 万。
3. 硬守门无论数据量多少都必须保留（§13.2 / §13.5）。
4. 到 8.2 万后先按现配置重跑一次曲线的末端点，验证外推是否弯折，再决定要不要上 DAgger。
